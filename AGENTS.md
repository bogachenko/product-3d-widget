# AGENTS.md

## 1. Назначение

Этот проект разрабатывается строго по методологии GRACE.

Код является производным артефактом утверждённых требований, семантического графа, архитектуры, контрактов, мысленных сценариев и критериев верификации.

Агент не должен самостоятельно переопределять замысел проекта на основании текущего кода.

Основная цепочка проекта:

```text
RequirementsAnalysis.xml
→ Technology.xml
→ DevelopmentPlan.xml
→ ModuleContracts.xml
→ ClassFunctionContracts.xml
→ код
→ тесты
→ семантические логи и трассы
→ верификация
```

Иерархия источников истины:

```text
RequirementsAnalysis.xml
выше Technology.xml
выше DevelopmentPlan.xml
выше ModuleContracts.xml
выше ClassFunctionContracts.xml
выше реализации
```

Нижестоящий артефакт не может молча противоречить вышестоящему.

---

## 2. Обязательный порядок чтения

Перед началом реализации или изменением кода агент обязан прочитать:

1. `RequirementsAnalysis.xml`
2. `Technology.xml`
3. `DevelopmentPlan.xml`
4. `ModuleContracts.xml`
5. `ClassFunctionContracts.xml`
6. `MentalScenarios.xml`
7. `VerificationCriteria.xml`
8. `validation-report.json`
9. релевантные инструменты в `tools/`

Нельзя начинать реализацию, прочитав только `DevelopmentPlan.xml`, контракт функции или отдельную часть задания.

Агент должен сначала определить релевантную ветвь семантического графа:

```text
требование
→ бизнес-процесс
→ модуль
→ контракт модуля
→ контракт класса или функции
→ мысленный сценарий
→ критерий верификации
→ целевой блок кода
```

Читать весь проект без необходимости не требуется. Нужно собирать контекст по стабильным идентификаторам и ссылкам из артефактов.

---

## 3. Условия перехода к реализации

Реализация разрешена только при одновременном выполнении следующих условий:

* соответствующее требование существует в `RequirementsAnalysis.xml`;
* требование связано с бизнес-процессом;
* модуль существует в `DevelopmentPlan.xml`;
* для модуля существует утверждённый контракт в `ModuleContracts.xml`;
* для создаваемого класса или функции существует контракт в `ClassFunctionContracts.xml`;
* основные сценарии описаны в `MentalScenarios.xml`;
* критерии проверки определены в `VerificationCriteria.xml`;
* `validation-report.json` не содержит неразрешённых ошибок или противоречий, запрещающих переход к коду.

Главное правило:

```text
Нет утверждённого контракта — нет реализации.
```

Если необходимого требования, связи, контракта, сценария или критерия нет, агент не должен придумывать его внутри кода.

В этом случае агент должен:

1. остановить реализацию затронутого элемента;
2. указать отсутствующий или противоречивый узел;
3. привести его стабильный ID либо место, где ID должен существовать;
4. сообщить, какой вышестоящий артефакт требует уточнения.

## 4. Правила генерации кода

Код должен создаваться как реализация утверждённого контракта.

Агент обязан:

* соблюдать ответственность модуля;
* соблюдать ответственность класса и функции;
* соблюдать `NON_RESPONSIBILITIES`;
* соблюдать входы и выходы;
* соблюдать предусловия и постусловия;
* сохранять инварианты;
* не создавать незаявленных побочных эффектов;
* соблюдать определённое поведение при ошибках;
* использовать только разрешённые зависимости;
* сохранять связи с требованиями и бизнес-процессами;
* реализовывать только утверждённую область задачи.

Агент не должен одновременно придумывать назначение функции и писать её реализацию.

Контракт функции является локальным уточнением цепочки:

```text
требование
→ архитектурный граф
→ контракт модуля
→ контракт функции
→ код
```

## 5. Семантическая разметка кода

Исходный код должен содержать парные XML-подобные семантические якоря.

Семантические якоря используются как:

* top-down каркас генерации;
* карта навигации агента;
* стабильные координаты для поиска;
* границы безопасного применения патчей;
* связь реализации с графом проекта.

Каждый значимый семантический блок должен иметь стабильный ID.

Нельзя создавать случайные ID, если соответствующий ID уже существует в артефактах.

Минимальная разметка значимого блока:

```text
<SEMANTIC_BLOCK id="стабильный ID блока">
    <INTENT>
        Назначение блока.
    </INTENT>

    <LINKS>
        <REQUIREMENT ref="ID требования" />
        <BUSINESS_PROCESS ref="ID бизнес-процесса" />
        <MODULE ref="ID модуля" />
        <MODULE_CONTRACT ref="ID контракта модуля" />
        <FUNCTION_CONTRACT ref="ID контракта функции" />
    </LINKS>

    реализация блока

</SEMANTIC_BLOCK>
```

В исходном коде разметка оформляется комментариями, допустимыми для используемого языка.

Пример:

```go
// <SEMANTIC_BLOCK id="BLOCK-ORDER-VALIDATION">
// <INTENT>
// Проверить возможность перехода заказа к следующему состоянию.
// </INTENT>
// <LINKS>
// <REQUIREMENT ref="REQ-ORDER-001" />
// <BUSINESS_PROCESS ref="BP-ORDER-CREATION" />
// <MODULE ref="MOD-ORDER" />
// <MODULE_CONTRACT ref="CONTRACT-MOD-ORDER" />
// <FUNCTION_CONTRACT ref="CONTRACT-VALIDATE-ORDER" />
// </LINKS>

func validateOrder(...) (...) {
	// Реализация утверждённого контракта.
}

// </SEMANTIC_BLOCK>
```

Разметка должна быть пропорциональна сложности и критичности.

Не нужно размечать каждую строку.

Отдельный семантический блок должен:

* решать одну понятную задачу;
* иметь самостоятельное намерение;
* иметь стабильные границы;
* быть доступным для отдельного поиска и изменения;
* ссылаться на вышестоящие узлы графа.

## 6. MODULE_MAP и структура модулей

Каждый значимый модуль должен иметь читаемую агентом карту структуры.

Карта должна позволять определить:

* назначение модуля;
* основные классы и функции;
* связи между блоками;
* реализуемые требования;
* сохраняемые инварианты;
* разрешённые зависимости;
* точки входа;
* тесты и события логов.

Карта модуля не заменяет `ModuleContracts.xml`.

Она служит навигацией от контракта модуля к его реализации.

## 7. Правила работы с контрактами

Контракт является семантическим щитом реализации.

При любом изменении агент обязан сравнить патч с:

```text
контрактом функции
→ контрактом модуля
→ DevelopmentPlan.xml
→ RequirementsAnalysis.xml
```

Если код и контракт противоречат друг другу, нельзя автоматически считать текущий код правильным.

Допустимы только два варианта:

1. код исправляется в соответствии с утверждённым контрактом;
2. реализация останавливается до осознанного изменения вышестоящего артефакта.

Запрещено:

* молча изменять смысл контракта;
* подгонять контракт под уже написанный код;
* удалять ограничение ради упрощения реализации;
* переносить ответственность между модулями без изменения архитектурного графа;
* добавлять побочный эффект, отсутствующий в контракте;
* расширять область функции на основании локального удобства.

## 8. Изменение существующего кода

Перед изменением существующего блока агент обязан определить:

* ID семантического блока;
* связанное требование;
* связанный бизнес-процесс;
* модуль;
* контракт модуля;
* контракт класса или функции;
* связанные мысленные сценарии;
* связанные критерии верификации;
* связанные тесты;
* связанные события логов и трассы.

Изменение должно применяться к семантическому блоку, а не к случайному диапазону строк.

После изменения необходимо проверить, затронуты ли:

* соседние блоки;
* интерфейсы;
* зависимости;
* состояния;
* инварианты;
* тестовые сценарии;
* события логирования;
* ссылки графа.

## 9. Распространение изменений

Изменение должно распространяться сверху вниз.

Правильная последовательность:

```text
изменено требование
→ обновлён бизнес-процесс
→ обновлён DevelopmentPlan.xml
→ обновлены контракты модулей
→ обновлены контракты классов и функций
→ обновлены MentalScenarios.xml
→ обновлены VerificationCriteria.xml
→ изменён код
→ обновлены тесты и ожидаемые трассы
→ выполнена верификация
```

Если задача требует изменения утверждённого требования, архитектуры или контракта, агент не должен начинать с патча кода.

## 10. Мысленные сценарии

Перед написанием реализации агент обязан проверить соответствующие сценарии из `MentalScenarios.xml`.

Мысленный сценарий должен быть сопоставлен с:

* входными данными;
* последовательностью действий;
* изменениями состояния;
* ветвлениями;
* ожидаемым результатом;
* инвариантами;
* запрещёнными действиями.

Мысленный сценарий используется для проверки плана.

Он не заменяет исполняемый тест.

```text
Мысленный тест = гипотеза и проверка архитектуры.
Исполняемый тест = наблюдаемое свидетельство.
```

---

## 11. Автоматические тесты

Тесты должны выводиться из утверждённых контрактов и критериев верификации.

Корректность определяется как:

```text
результат тестов
+ соблюдение контрактов
+ сохранение инвариантов
+ допустимый путь выполнения
+ отсутствие регрессий
```

Обязательные уровни проверки:

1. компиляция;
2. типы;
3. схемы;
4. ограничения хранилища данных;
5. предусловия;
6. постусловия;
7. инварианты;
8. детерминированные assertions;
9. интеграционные проверки;
10. регрессионные проверки;
11. проверка семантической трассы;
12. независимая оценка критических изменений.

Нельзя удалять существенные assertions.

Допустимо удалять или исправлять только:

* бессодержательные проверки;
* хрупкие проверки деталей реализации;
* проверки, противоречащие утверждённому контракту.

Агент реализации не должен бесконтрольно изменять одновременно:

```text
код
+ контракт
+ тест
+ критерий приёмки
```

## 12. Два уровня тестовой обратной связи

Каждый тестовый запуск должен выдавать:

### Бинарный результат

```text
PASS
FAIL
```

Он используется для приёмки изменения.

### Диагностический результат

При сбое необходимо предоставить:

* ID теста;
* ID требования;
* ID контракта;
* нарушенное свойство;
* ожидаемое значение или состояние;
* фактическое значение или состояние;
* первую точку расхождения;
* ID трассы;
* ID семантического блока;
* релевантные события логов.

Пример структуры:

```xml
<TEST_FEEDBACK id="TF-UNIQUE-ID">
    <VERDICT>FAIL</VERDICT>

    <TEST ref="TEST-UNIQUE-ID" />
    <REQUIREMENT ref="REQ-ENTITY-001" />
    <CONTRACT ref="CONTRACT-CREATE-ENTITY" />
    <TRACE ref="TRACE-ENTITY-001" />

    <FAILED_PROPERTY ref="INV-UNIQUE-ID">
        Идентификатор должен оставаться уникальным.
    </FAILED_PROPERTY>

    <EXPECTED>
        duplicate_count=0
    </EXPECTED>

    <ACTUAL>
        duplicate_count=2
    </ACTUAL>

    <FIRST_DIVERGENCE>
        <FUNCTION ref="createEntity" />
        <SEMANTIC_BLOCK ref="BLOCK-ID-GENERATION" />
    </FIRST_DIVERGENCE>
</TEST_FEEDBACK>
```

Сообщение только `TEST FAIL` недостаточно для цикла исправления.

## 13. Агентно-доступная тестовая поверхность

Перед созданием нового тестового интерфейса агент обязан изучить каталог `tools/`.

Для проверки приложения следует использовать существующие:

* CLI;
* API;
* Tools;
* средства загрузки тестовых данных;
* средства получения состояния;
* средства получения логов и трасс;
* средства очистки тестовой среды.

Агент должен предпочитать предметные операции приложения вместо медленного взаимодействия через GUI, если соответствующий Tool или CLI уже существует.

GUI-тесты используются для пользовательских E2E-сценариев, но не являются единственным способом проверки.

Тестовая последовательность:

```text
сценарий
→ вызовы Tools
→ исполнение приложения
→ состояние
→ assertions
→ семантические логи
→ трасса
→ отчёт
```

## 14. Семантические логи

Каждое значимое событие должно быть связано с семантическим графом.

Минимальные поля события:

```text
EVENT_ID
TIMESTAMP
SEVERITY
TRACE_ID или CORRELATION_ID
MODULE
FUNCTION или SEMANTIC_BLOCK
CONTRACT_ID
REQUIREMENT_ID
INTENT
RESULT
REASON
STRUCTURED_DATA
```

Пример:

```xml
<LOG_EVENT
    id="EVT-ORDER-VALIDATION-FAILED"
    timestamp="..."
    severity="ERROR"
    trace_id="TRACE-..."
    module="MOD-ORDER"
    function="validateOrder"
    contract="CONTRACT-VALIDATE-ORDER"
    requirement="REQ-ORDER-001">

    <INTENT>
        Проверить возможность перехода заказа к следующему состоянию.
    </INTENT>

    <RESULT>VALIDATION_FAILED</RESULT>
    <REASON>INVALID_QUANTITY</REASON>

    <DATA>
        order_id=483921
        quantity=-2
    </DATA>
</LOG_EVENT>
```

Для длинных логов должен существовать `LOG_MAP`, позволяющий перейти:

```text
LOG_MAP
→ trace
→ событие
→ контракт
→ семантический блок
→ причина
```

Логи не должны состоять только из неструктурированного текста.

---

## 15. Log-Driven Development

Для значимых бизнес-сценариев должна быть определена ожидаемая трасса.

Проверяется:

* последовательность событий;
* обязательные события;
* запрещённые события;
* переходы состояний;
* итоговое состояние;
* связь событий с контрактами.

Пример:

```xml
<EXPECTED_TRACE id="TRACE-ORDER-CREATE">
    <STEP order="1" event="ORDER_VALIDATED" />
    <STEP order="2" event="STOCK_RESERVED" />
    <STEP order="3" event="ORDER_SAVED" />

    <FORBIDDEN_EVENT event="UNRELATED_ENTITY_CHANGED" />

    <FINAL_STATE>
        order_status=SAVED
        stock_reserved=true
    </FINAL_STATE>
</EXPECTED_TRACE>
```

Семантическая оценка трассы дополняет, но не заменяет детерминированные проверки.

## 16. Форматы данных и контекста

Для больших документов, графов, контрактов и семантических блоков использовать:

* XML;
* XML-подобную разметку;
* Markdown с явными секциями;
* именованные блоки со стабильными ID.

JSON использовать для:

* API;
* tool calling;
* сериализации;
* строгих машинных схем;
* программного обмена.

```text
Длинный контекст для LLM
→ XML-like или Markdown

Машинный обмен
→ JSON
```

## 17. Запрещённые действия

Агенту запрещено:

* начинать реализацию без чтения обязательных артефактов;
* писать класс или функцию без утверждённого контракта;
* создавать архитектуру внутри реализации;
* придумывать отсутствующее требование;
* расширять ответственность функции;
* расширять ответственность модуля;
* добавлять незаявленные побочные эффекты;
* менять контракт под ошибочный код;
* ослаблять критерий ради прохождения теста;
* считать текущий код более достоверным, чем утверждённый контракт;
* считать мысленный сценарий доказательством работы;
* считать успешный smoke-тест полной верификацией;
* заменять строгие проверки заключением LLM;
* оставлять значимые блоки без семантических якорей;
* оставлять значимые события без стабильных ID;
* использовать строки файла как основные координаты патча;
* изменять несвязанные блоки;
* одновременно менять код, контракт и критерий приёмки без отдельного утверждённого изменения замысла;
* объявлять работу завершённой при наличии непроверенных критериев;
* обходить существующие инструменты из `tools/` без причины.

## 18. Критерии завершения реализации

Задача считается выполненной только если:

* реализовано утверждённое требование;
* соблюдён `DevelopmentPlan.xml`;
* соблюдён контракт модуля;
* соблюдены контракты классов и функций;
* код содержит необходимые семантические якоря;
* все ссылки используют стабильные ID;
* мысленные сценарии сопоставлены с реализацией;
* критерии из `VerificationCriteria.xml` проверены;
* компиляция успешна;
* детерминированные тесты успешны;
* интеграционные и регрессионные проверки успешны;
* инварианты сохранены;
* незаявленные побочные эффекты отсутствуют;
* фактические трассы соответствуют ожидаемым;
* значимые события имеют семантические логи;
* граф, контракты, код, тесты и логи синхронизированы;
* `validation-report.json` не содержит неразрешённых нарушений.

---

## 19. Формат итогового отчёта агента

После реализации агент должен сообщить:

```text
1. Какие требования реализованы.
2. Какие ID модулей и контрактов затронуты.
3. Какие семантические блоки созданы или изменены.
4. Какие файлы изменены.
5. Какие тесты и критерии выполнены.
6. Какие traces проверены.
7. Какие инварианты подтверждены.
8. Остались ли противоречия или непроверенные элементы.
```

Если работа не завершена, агент должен явно указать:

* что осталось;
* какой артефакт или узел блокирует продолжение;
* какие проверки ещё не выполнены.

## 20. Главное правило проекта

```text
Сначала утверждённый граф замысла.
Затем утверждённые контракты.
Затем семантически размеченный код.
Затем тесты, логи, трассы и полная верификация.
```

Любое изменение должно оставаться прослеживаемым по цепочке:

```text
требование
→ бизнес-процесс
→ модуль
→ контракт
→ семантический блок
→ тест
→ trace
→ событие лога
```
